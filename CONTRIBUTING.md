# Contributing to GroupsMath

Thank you for your interest in contributing to **GroupsMath**!

GroupsMath is a Python library focused on computational and educational group theory. Contributions are welcome, whether they involve new functionality, bug fixes, mathematical improvements, documentation, tests, or suggestions.

## Getting started

Before contributing, please:

1. Read the project documentation.
2. Check the existing issues and pull requests to avoid duplicating work.
3. Make sure your changes are consistent with the mathematical and software design of the project.
4. Test your changes before submitting a pull request.

## Code contributions

When contributing code:

- Follow the existing Python style and project structure.
- Prefer clear and mathematically meaningful names.
- Keep implementations as general as reasonably possible.
- Avoid introducing unnecessary dependencies.
- Add or update tests for new functionality and bug fixes.
- Document public classes, functions, and methods when appropriate.
- Do not sacrifice mathematical correctness for performance without documenting the trade-off.

Because GroupsMath is a mathematical library, correctness is particularly important. Algorithms should be checked against known examples and mathematical properties whenever possible.

## Mathematical contributions

Contributions involving mathematical algorithms are especially welcome.

If you propose a new algorithm or mathematical construction, please provide enough information to explain:

- what mathematical object or problem it addresses;
- the algorithm or underlying mathematical idea;
- any assumptions or limitations;
- relevant references, when applicable;
- examples that can be used to verify the implementation.

For non-trivial algorithms, a mathematical explanation in the documentation is preferred over an implementation without context.

## Documentation

Documentation contributions are welcome.

Please keep the documentation consistent with the mathematical notation and terminology used throughout the project. If you introduce a new public feature, consider documenting both its purpose and its mathematical interpretation.

## Tests

New functionality should preferably include tests.

Tests should cover normal cases as well as relevant edge cases. For mathematical functionality, examples involving well-known groups are particularly useful.

For example, implementations involving cyclic, symmetric, or quotient groups should be tested against cases whose results are known independently.

## AI-assisted development

Generative AI tools may be used during the development of GroupsMath, including for programming, debugging, refactoring, testing, and documentation.

AI-generated material is reviewed, modified, and tested by the project author before being incorporated into the project.

Contributors may also use AI-assisted development tools, but they remain responsible for the code and documentation they submit, including its correctness, originality, licensing, and compatibility with this project's license.

Do not submit material generated by an AI tool without reviewing it first.

## Pull requests

Pull requests should:

- Clearly describe what has been changed.
- Explain the motivation for the change when it is not obvious.
- Include tests when appropriate.
- Keep unrelated changes out of the same pull request.
- Ensure that existing tests continue to pass.

For substantial changes, opening an issue or discussing the proposed design before implementing it is encouraged.

## Reporting bugs

When reporting a bug, please include:

- a clear description of the problem;
- the expected behaviour;
- the actual behaviour;
- a minimal reproducible example, if possible;
- the Python version;
- the GroupsMath version;
- any relevant error messages or tracebacks.

## License

By contributing to GroupsMath, you agree that your contribution may be distributed under the license used by the project.

Please make sure that you have the right to submit any code, documentation, or other material that you contribute.

## Code of conduct

Please be respectful and constructive when interacting with other contributors.

Disagreements about implementation or mathematical details are welcome; personal attacks and harassment are not.
